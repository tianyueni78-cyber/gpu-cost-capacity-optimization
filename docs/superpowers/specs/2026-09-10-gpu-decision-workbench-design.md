# GPU决策工作台设计规格

## 1. 决策结论

采用“一个平台＋四个可独立购买模块”：GPU Data、GPU Optimize、GPU Improve和GPU Forecast。统一平台负责共享数据与状态，模块负责独立客户问题和独立交付。

这不是四套重复系统，也不是一个无法拆分的大产品。四个模块通过稳定的输入输出契约连接。

## 2. 产品目标

把可信的GPU成本、使用、SLA和业务需求数据转化为可审核的现状、优化机会、决策方案和实际收益证据。

成功不是生成更多图表，而是让客户能够：

1. 判断数据是否足以支持结论；
2. 定位成本和容量问题；
3. 比较互不重复的行动方案；
4. 指定负责人并记录执行；
5. 使用可比基线验证实际效果。

## 3. 模块契约

| 模块 | 最小输入 | 稳定输出 | 独立价值 |
|---|---|---|---|
| GPU Data | 清单、使用、账单、SLA | 审计、基线、线索 | 可信地看清现状 |
| GPU Optimize | 合格基线与约束 | 机会卡、方案、决策包 | 决定调整什么 |
| GPU Improve | 批准行动与行动后数据 | 状态、实际收益、副作用 | 证明行动价值 |
| GPU Forecast | 历史业务量、资源与事件 | 预测区间、容量情景 | 规划未来容量 |

模块只依赖契约，不依赖另一个模块的界面。客户提供等价合格数据时，可以跳过GPU Data直接进入其他模块。

## 4. 共享领域对象

- `AnalysisProject`：范围、目标、币种、负责人和约束；
- `DatasetVersion`：映射、覆盖期间、审计状态和来源摘要；
- `MetricResult`：指标值、粒度、口径、来源和规则版本；
- `Finding`：数据或业务调查线索，不包含未经证明的行动收益；
- `Opportunity`：行动、证据、潜在价值、风险和确认项；
- `Scenario`：一组已去重的机会及重算结果；
- `Action`：批准方案中的执行责任与状态；
- `BenefitMeasurement`：基线、实际结果、差异和可信度。

## 5. 工作流与准入门

### 数据门

字段无法映射、金额无法对账、关键业务键冲突或核心关联失败时，阻断依赖结论。警告随数据版本传播到所有输出。

### 事实门

只有完成成本、资源、利用率和SLA口径对账后，才能生成优化机会。没有SLA或备用容量证据时，不得把低利用率转成低风险缩容建议。

### 决策门

机会必须包含证据、行动、潜在收益、风险、适用条件和人工确认项。方案必须经过冲突检测和收益去重。

### 执行门

第一版不自动写入生产环境。用户批准后生成行动清单，由客户执行并记录状态。

### 验证门

实际收益必须使用行动前后可比口径，并同时观察成本、业务量、容量和SLA。无法形成反事实基线时标记为“无法验证”。

## 6. 页面和状态

页面按任务组织：项目与数据、GPU Data、GPU Optimize、GPU Improve、GPU Forecast。

```text
项目草稿 → 数据待确认 → 审计阻断 / 分析就绪
分析就绪 → 机会待审核 → 方案已批准
方案已批准 → 执行中 → 待验证
待验证 → 已验证 / 部分实现 / 未实现 / 负面影响 / 无法验证
```

状态变化必须记录时间、操作者和所用数据版本。第一版本地单用户模式可把操作者记为用户输入，不建设账号系统。

## 7. 计算边界

- 使用实际净成本，不以目录价替代账单；
- 共享和未归属费用单独展示；
- 使用优化与费率优化分开计算；
- 近期节省、续约节省和避免采购分开；
- 同一资源上的互斥机会不得累加；
- 理论、批准和实际节省不得混用；
- 预测必须以区间进入容量情景；
- 所有建议必须保留公式、输入和适用范围。

## 8. 错误处理

- 输入错误：指出表、字段和受影响模块；
- 规则不足：标记待确认，不用历史数据创造业务规则；
- 无可行方案：展示冲突约束，不伪造节省；
- 数据不足：降低结论或拒绝生成；
- 执行结果缺失：保持待验证，不自动视为成功。

## 9. 测试要求

- 数据版本与映射不可静默变化；
- 连接、归属和聚合前后金额守恒；
- 阻断规则确实阻止后续模块；
- 机会规则在边界条件下无误报；
- 方案冲突和收益去重具有反例测试；
- SLA与最低备用容量始终形成硬约束；
- 实际收益使用可比期间和业务量；
- 模块输出契约允许独立测试。

## 10. 实施顺序

1. 整合并发布已完成的GPU Data能力；
2. 固定共享指标和模块输出契约；
3. 开发GPU Optimize机会卡；
4. 开发方案模拟、冲突检查和决策包；
5. 开发GPU Improve行动台账与收益验证；
6. 最后开发GPU Forecast并接入方案情景；
7. 真实客户验证前不建设自动执行和多租户SaaS。

## 11. 官方设计依据

- FinOps Foundation要求Inform、Optimize、Operate循环运行，并区分使用优化与费率优化；
- AWS成本优化覆盖财务管理、使用意识、资源选择、共享、供需与持续复查；
- Google FinOps Hub区分潜在与实际节省，并对重叠建议去重；
- Vantage把证据、预计收益和修复步骤组合成建议；
- NVIDIA Run:ai表明GPU资源分配需要同时考虑利用率、配额、优先级和公平共享。
