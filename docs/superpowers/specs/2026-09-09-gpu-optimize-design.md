# GPU Optimize 产品设计

## 1. 产品定位

GPU Optimize 把可信的 GPU 成本与资源基线，转换成满足需求、SLA、合同和硬件约束的可审批配置方案。

它解决的问题是：客户知道存在浪费或容量矛盾，但无法回答“应该调整什么、调整多少、成本与风险如何变化”。

GPU Optimize 不负责预测未来需求、验证实施后的实际效果，也不自动修改云资源、Kubernetes 或生产集群。

## 2. 产品边界

| 输入或环节 | 负责人 |
| --- | --- |
| 数据清洗、成本对账、当前基线 | GPU Data，或客户提供的已审计标准数据 |
| 未来需求和峰值 | 用户输入，或 GPU Forecast |
| SLA、备用容量、合同和共享限制 | 产品规则结构化，用户确认 |
| 把业务要求转换成数学约束 | GPU Optimize |
| 搜索满足约束的低成本组合 | GPU Optimize 内部求解器 |
| 风险解释、方案比较和审批材料 | GPU Optimize |
| 审批和生产执行 | 客户负责人 |
| 实施后效果验证 | GPU Improve |

求解器是 GPU Optimize 的内部计算引擎，不是第五个产品。求解结果必须经过产品规则解释，不能直接作为执行命令。

## 3. 三个优化模块

三个模块属于同一个产品，共用基线、约束、求解接口、方案比较和审批报告。对外只展示已经实现并验证的模块；未完成模块不得展示虚假结果。

### 3.1 采购组合优化

**痛点**

- 按需 GPU 占比过高；
- 预留或承诺采购买多、买少或期限不合适；
- 采购结构与稳定需求、峰值需求不匹配。

**输入**

- 当前采购结构和实际费率；
- 最低稳定需求、峰值需求和分析期间；
- 合同期限、最低承诺和退出限制；
- 允许使用的采购类型及按需比例限制。

**输出**

- 按需、预留和承诺采购数量；
- 当前成本、方案成本和理论节省；
- 合同锁定风险；
- 需求上升或下降时的敏感性。

### 3.2 容量分配优化

**痛点**

- 团队之间同时存在闲置和容量不足；
- 各团队重复保留备用容量；
- 共享池规模和团队配额不合理。

**输入**

- 当前团队配额、使用量和峰值；
- SLA、备用容量和优先级；
- GPU 型号兼容关系；
- 可以共享、禁止共享和地域限制。

**输出**

- 各团队保留、释放和共享的 GPU 数量；
- 共享池规模；
- 调整后的容量余量和 SLA 风险；
- 跨团队依赖及负责人确认事项。

### 3.3 运行配置优化

**痛点**

- 整卡分配造成浪费；
- MIG 切分与工作负载不匹配；
- 时间切片产生不可接受的性能或隔离风险；
- 节点池配置过多或利用不均。

**输入**

- GPU 型号和支持能力；
- 工作负载的显存、计算和隔离要求；
- 整卡、MIG、时间切片的使用限制；
- 节点池和 Kubernetes 环境约束。

**输出**

- 整卡、MIG 或时间切片建议；
- 节点池配置和适用工作负载；
- 性能、显存和故障隔离风险；
- 实施前验证与回滚要求。

## 4. 用户工作流

### 第 1 页：基线接入

从 GPU Data 导入，或上传经过审计的标准数据。缺少成本对账、资源关联或关键约束时阻断求解。

### 第 2 页：目标与约束

用户选择降低成本、释放容量、缓解容量不足或调整采购，并确认需求、峰值、SLA、备用容量、合同、共享和硬件限制。系统必须区分不可违反的硬约束与用于比较方案的软偏好。

### 第 3 页：容量与运行优化

先计算团队保留、释放和共享容量，再在硬件与隔离条件允许时生成整卡、MIG 或时间切片建议。任何无法验证的兼容性都应成为阻断或人工确认项。

### 第 4 页：采购优化

使用容量与运行调整后的稳定需求生成采购组合，展示数量、费率、成本、理论节省、合同风险和需求敏感性。未启用该模块时明确显示“不适用”。不得对计划释放的容量重复购买长期承诺。

### 第 5 页：方案比较

并列展示当前方案、最低成本方案、低风险方案和用户自定义方案。每个方案统一比较成本、容量余量、SLA 风险、合同风险和变更范围。

### 第 6 页：审批报告

导出输入口径、约束、调整明细、理论节省、风险、前置条件、责任人、验证步骤和回滚要求。报告不得生成生产执行命令。

## 5. 求解规则

第一版采用分层目标，而不是把成本和风险混成一个难以解释的权重分数：

1. 所有硬约束必须满足；
2. 在可行方案中最小化实际成本；
3. 成本相同时，优先变更更少、风险更低的方案。

如果不存在可行方案，产品应指出冲突约束和需要用户调整的输入，不得返回一个违反 SLA 或合同限制的“最优方案”。

理论节省等于当前可比成本减去方案可比成本。实际账单优惠、税费、退出费用和无法取得的合同信息必须单独披露，不得默认为零。

## 6. 安全规则

- 用户必须确认所有业务约束和自动映射；
- 低利用率不能单独成为回收资源的依据；
- 采购建议必须使用实际费率，并披露未覆盖的折扣和退出成本；
- GPU 共享必须检查显存、性能、故障隔离和硬件兼容性；
- 所有输出都是待审批方案，不自动执行生产变更；
- 未实现或未验证的模块不得出现在对外可用功能中。

## 7. 交付顺序

设计完整覆盖三个模块，开发按以下顺序交付：

```text
公共基线与约束
→ 容量分配优化
→ 运行配置优化
→ 采购组合优化
→ 联合方案比较与审批报告
```

每个阶段必须能够独立生成真实、可解释的结果后才能对外展示。后续模块不阻塞已完成模块单独销售。

## 8. 验收标准

- 相同输入与约束产生稳定、可复核的结果；
- 所有候选方案满足已确认的硬约束；
- 当前成本与方案成本使用相同口径；
- 每项调整都能追溯到输入、约束和计算规则；
- 无可行解时能解释冲突，而不是放松约束；
- 报告明确区分理论节省、潜在风险和客户决策；
- 未上线模块不对外展示为可用能力。

## 9. 专业依据

- [FinOps Usage Optimization](https://www.finops.org/framework/capabilities/workload-optimization/)：优化需要同时考虑利用率、性能、可用性、业务约束和实施成本；
- [FinOps Rate Optimization](https://www.finops.org/framework/capabilities/rate-optimization/)：采购费率优化与资源使用优化是相关但不同的决策；
- [AWS Compute Optimizer](https://docs.aws.amazon.com/compute-optimizer/latest/ug/view-ec2-recommendations.html)：建议应呈现预计利用率、价格和性能风险；
- [Azure Advisor 成本建议](https://learn.microsoft.com/en-us/azure/advisor/advisor-cost-recommendations)：节省估算需要考虑历史窗口、实际费率和承诺折扣；
- [NVIDIA GPU Sharing](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/gpu-sharing.html)：MIG 与时间切片具有不同的显存和故障隔离能力。
