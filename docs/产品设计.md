# GPU Data｜产品设计

## 1. 产品定位

**一句话承诺：** 把 GPU 资源、使用、账单和 SLA 数据转换为可信现状，并指出最值得调查的资源与成本问题。

目标客户是 GPU 支出较高、但缺少专职 FinOps 能力的中小型 AI 团队。直接用户通常是基础设施负责人、平台负责人或技术顾问。

GPU Data 回答三个问题：

1. 钱花在哪里；
2. GPU 如何被配置和使用；
3. 哪里存在值得负责人核查的异常。

它不回答应该释放多少资源、能够节省多少钱或未来需要多少 GPU。这些分别属于 GPU Optimize 和 GPU Forecast。

## 2. 产品形态

第一版是 Streamlit 本地 Web 应用。程序和数据在客户电脑上运行，不需要登录、服务器、数据库、GPU 或付费云服务。浏览器只是操作界面，因此第一版不是 SaaS。

公开演示只能使用合成数据；真实数据只进入本地客户版。只有付费试点证明持续监控需求后，才评估 SaaS。

## 3. 四页工作流

### 数据接入

上传资源清单、使用记录、云账单和团队 SLA，确认字段映射并运行审计。审计覆盖主键、必填值、数值范围、日期、采购方式、账单公式和跨表关联。

结果分为通过、警告和阻断。任何异常阻断项都会停止后续分析；警告保留在最终报告中。

### 当前状况

展示：

- 原始费用、折扣和净成本；
- 团队、GPU 型号、区域和采购方式的成本归属；
- GPU 库存、已分配数量、活跃数量；
- GPU 核心利用率和显存利用率的中位数与 P95；
- 遥测、SLA 和成本归属覆盖率；
- 无法归属的净成本。

缺失遥测显示“数据不足”，不补零。聚合与关联前后的净成本必须一致。

### 调查线索

第一版支持五类确定性线索：

1. 高成本且持续低活跃；
2. 已分配数量与活跃数量明显分离；
3. 账单缺少直接团队归属；
4. SLA 观测低于约束；
5. 承诺采购缺少充分使用证据。

每条线索包含观察、期间、证据、相关成本、限制条件、来源记录和负责人核查问题。相关成本只是问题影响范围，不是可节省金额。

### 诊断报告

页面展示并导出：

- Markdown 管理诊断报告；
- `metrics.csv` 指标明细；
- `signals.csv` 调查线索；
- `data_quality.csv` 数据质量结果。

CSV 使用 UTF-8 BOM，便于在中文 Excel 中直接打开。

## 4. 计算与判断原则

- 成本以账单净成本为主，原价和折扣分列；
- 未归属成本单列，不强行摊派；
- 库存、已分配、活跃数量和 GPU 利用率不互相替代；
- GPU 核心与显存利用率分别展示；
- 不用单个平均值判断异常，结合中位数、P95、峰值、低活跃观测比例和覆盖期；
- 低利用率必须结合 SLA、排队、备用容量和业务事件人工核查；
- 承诺成本不能描述为合同期内可立即减少；
- 每条线索必须能够回到来源表、期间和记录数量。

## 5. 技术结构

```text
Streamlit 四页界面
    ↓
字段映射与数据审计
    ↓
成本和资源基线
    ↓
确定性调查线索
    ↓
Markdown 与 CSV 导出
```

核心逻辑位于独立的 pandas 纯函数中，界面只负责会话状态、展示和下载。当前不增加数据库、API 服务、求解器或云厂商 SDK。

## 6. 验收标准

- 四种不同业务角色的数据只能从明确入口上传；
- 严重数据问题阻断所有分析输出；
- 成本归属前后净成本完全一致；
- 可选遥测缺失时显示数据不足；
- 五类线索具备证据、限制和核查问题；
- 页面和报告不出现预测、配置方案或节省承诺；
- 四类报告可以正常下载；
- 全部自动测试、Python 编译和 Streamlit 健康检查通过。

## 7. 商业验证

第一阶段按单次诊断收费，而不是销售软件账号。使用 30 分钟试点证明客户能更快定位真实调查对象。

进入 GPU Optimize 前必须获得以下证据：至少三名目标用户审阅结果，两名确认线索推动了真实调查，一名接受付费或明确报价的试点。

## 8. 暂不实现

- 容量或成本预测；
- 回收、共享、迁移和采购建议；
- 理论节省与 ROI；
- 自动调度或资源修改；
- 多租户 SaaS、在线支付和实时云接入。
