# GPU Optimize 容量分配：30 分钟客户试点

## 试点目标

验证客户能否用真实脱敏数据确认需求与 SLA 约束，获得满足硬约束、可解释且可审批的容量分配方案。

## 客户准备

- 同一期间的 GPU 资源清单、使用记录、云账单和团队 SLA；
- 各团队确认的峰值需求；
- 能够确认共享边界和最终审批责任的人。

## 30 分钟流程

### 0—8 分钟：基线接入

上传四张 CSV、确认字段映射并运行审计。任何阻断项都必须停止求解；不得为了演示绕过数据问题。

### 8—15 分钟：确认约束

按团队、GPU 型号和地域确认峰值需求与 SLA 备用容量。逐资源池选择不可共享、团队内共享或跨团队共享，并确认系统默认峰值是否符合业务事实。

### 15—22 分钟：容量求解

运行求解器，对比当前、安全调整和低变更方案。验证所有团队保留容量不低于确认需求加备用容量；验证 H100/A100 与地域互不替代；无可行方案时检查具体兼容范围的缺口解释。

### 22—27 分钟：口径复核

逐资源池核对 GPU 数量、实际小时费率和受影响成本，并确认明细汇总等于方案总额。明确受影响成本不是已验证节省，共享容量也不会自动降低现有账单。

### 27—30 分钟：审批导出

设置待确认、待审批、推迟或不适用状态，下载审批报告、建议、资源池调整和约束快照 CSV。请客户确认责任人、验证步骤和回滚要求；产品不执行生产变更。

## 成功标准

- 四张表能与客户来源对账；
- 约束由客户明确确认；
- 所有可行方案满足硬约束；
- 不同型号和地域没有未经授权的替代；
- `none` 和 `team` 权限没有产生越权跨团队调整；
- 不可行时准确解释容量缺口；
- 资源池成本明细与方案汇总一致；
- 客户理解受影响成本、理论节省和实际节省的区别；
- 导出材料足以支持一次内部评审。

## 记录结果

记录字段映射问题、约束缺失、误报、漏报、求解时间和客户是否愿意用该报告发起审批。相同问题在多个试点重复出现后，再进入产品规则。
