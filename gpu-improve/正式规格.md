# GPU Improve 正式规格

## 1. 产品目标

GPU Improve 面向 FinOps、云基础设施负责人和平台团队，用于跟踪已批准 GPU 优化行动，并以可复算证据判断预计收益是否真正实现，以及行动是否损害业务容量或 SLA。

产品不把“执行完成”等同于“收益实现”，也不把“避免未来采购”计入已实现账单节省。

## 2. 专业对标原则

每项核心能力必须记录参考标准、采用部分、未采用部分及原因：

| 能力 | 专业依据 | 本产品采用 | 第一版不采用 |
|---|---|---|---|
| 行动生命周期 | FinOps Operate | 负责人、状态、执行、度量和持续复盘 | 自动修改生产资源 |
| 收益台账 | Google Cloud FinOps Hub | 区分潜在与已实现收益 | 云厂商账号自动采集 |
| 收益去重 | AWS Cost Optimization Hub | 识别互斥行动和重叠收益 | 全云资源推荐目录 |
| 业务量归一化 | FinOps Unit Economics | 成本与请求、任务、页面或其他业务单位关联 | 跨企业统一单位基准 |
| 有效成本 | FOCUS | 使用有效成本、承诺摊销和适用期间 | 完整实现所有 FOCUS 字段 |

专业对标决定计算与验收规则，但不要求复制成熟平台的全部功能。

## 3. 第一版边界

### 支持

- 从 GPU Optimize 导入已批准行动包；
- 上传标准行动 CSV；
- 在网页中手动新增或修改行动；
- 邮箱登录和用户数据隔离；
- 行动状态与变更历史；
- 行动前基线冻结；
- 行动后数据导入与可比性检查；
- 按行动类型选择收益验证方法；
- SLA 与业务副作用检查；
- 收益台账、Markdown 摘要和 CSV 明细导出。

### 不支持

- 自动执行云资源或 Kubernetes 变更；
- 企业组织、多人审批和复杂角色权限；
- 长期保存原始客户账单与使用明细；
- 缺乏反事实证据时强行声明收益；
- 把 GPU Forecast 的预测模型复制到本产品。

## 4. 页面工作流

```text
行动导入 → 执行台账 → 收益验证 → 收益复盘
```

### 4.1 行动导入

用户选择 GPU Optimize 导出、标准 CSV 或手动新增。系统确认行动类型、资源对象、负责人、批准时间、执行时间、预计收益、实施成本和观察范围。

缺少资源对象、行动类型或基线范围时，不允许进入正式验证。

### 4.2 执行台账

用户按状态、负责人、团队和行动类型筛选行动。状态变化必须沿合法路径推进，并追加操作者、时间和备注，不得覆盖历史。

```text
待批准 → 已批准 → 执行中 → 已执行 → 待验证
                         ├→ 已取消
                         └→ 已回滚

待验证 → 已验证 / 部分实现 / 未实现 / 负面影响 / 无法验证
```

### 4.3 收益验证

用户上传行动后成本、业务量、容量、利用率和 SLA 数据。系统先审计数据，再检查行动前后期间、资源范围、成本口径、业务单位、价格和业务结构是否可比。

通过准入后，系统按照行动类型选择验证方法，并展示公式、输入、反事实成本、实际成本、实施成本、收益和证据等级。

### 4.4 收益复盘

系统汇总预计、批准、已执行和已验证收益，单独展示成本规避，呈现 SLA、容量和业务量变化，并列出未实现、负面影响和无法验证原因。

## 5. 数据模型

Supabase 保存以下对象：

| 对象 | 核心内容 |
|---|---|
| `projects` | 所有者、项目范围、币种、时区 |
| `actions` | 行动类型、资源对象、负责人、预计收益、实施成本 |
| `action_events` | 状态、操作者、发生时间、备注 |
| `baselines` | 数据版本、范围、期间、口径和行动前汇总指标 |
| `measurements` | 行动后成本、业务量、容量、利用率和 SLA |
| `benefit_results` | 验证方法、反事实、实际收益、证据等级和结论 |

原始 CSV 只在当前 Streamlit 会话中处理。Supabase 只保存行动、文件指纹、审计摘要、汇总指标和验证结果。

基线冻结后不得覆盖；修正时创建新版本。每项收益必须关联行动、基线版本、观察期间和公式版本。

## 6. 验证方法

### 6.1 缩容、关闭资源和容量共享

在成本与业务量具有合理比例关系、行动前后业务单位一致时：

```text
行动前单位成本 = 行动前有效成本 / 行动前业务量
反事实成本 = 行动前单位成本 × 行动后业务量
已验证收益 = 反事实成本 − 行动后实际有效成本 − 实施成本
```

固定成本与变动成本必须分开。承诺期内不可取消的固定费用不得随业务量同比缩放。

### 6.2 预留采购和节省计划

```text
费率收益 = 按需等价成本 − 实际有效成本 − 实施成本
```

必须核对承诺适用期间、摊销成本、覆盖率和未使用承诺；不得使用业务量归一化公式替代费率收益公式。

### 6.3 GPU 型号替换

使用相同业务量或同类工作负载比较成本、吞吐、延迟、失败率和 SLA。工作负载结构不可比时拒绝给出正式收益。

### 6.4 流程或调度优化

比较单位业务成本，同时检查活跃 GPU、利用率、排队时间、延迟和 SLA。只改善利用率但未改善成本或业务价值时，不声明财务收益。

### 6.5 避免采购

记录为成本规避：

```text
成本规避 = 经批准的原采购基线 − 调整后的采购计划
```

成本规避单独展示，不进入已实现账单节省。

## 7. 可比性与证据等级

### 可比性检查

- 前后资源与团队范围一致；
- 观察期间长度及工作日结构可比；
- 成本使用相同币种和有效成本口径；
- 业务量单位与业务结构可比；
- 执行调整期已从稳定观察期排除；
- 价格变化、迁移、故障和业务事件已识别；
- SLA 指标和目标定义一致。

### 证据等级

- **高**：范围可比、字段完整、公式适配、观察期充分；
- **中**：使用经说明的历史平均或存在轻微结构变化；
- **低**：只能估算，不进入正式已验证收益；
- **无法验证**：基线、范围、口径或行动后数据不足。

历史平均只有在业务量、价格、范围、趋势和季节性稳定时才能使用，并标记为中等证据。复杂变化无法可靠拆分时，系统必须拒绝计算。

## 8. 重叠与副作用

- 同一资源、相同期间的互斥行动只能保留一个收益；
- 前一行动已改变后续行动基线时，后续行动必须使用新基线；
- 已实现收益、成本规避和实施成本分别核算；
- SLA、业务容量、排队、延迟或失败率恶化时标记副作用；
- 副作用超过用户确认阈值时，结论为“负面影响”并展示回滚建议。

## 9. 数据库与安全

- 使用 Supabase PostgreSQL、邮箱登录和 Row Level Security；
- 每个用户只能访问自己拥有的项目及其子记录；
- 服务密钥和连接信息保存在 Streamlit Secrets，不进入 Git；
- 第一版免费环境只用于开发、作品集和合成数据演示；
- 真实客户原始账单不得上传公共演示环境；
- 免费项目可能因低活跃暂停，不能作为生产 SLA 承诺。

## 10. 错误处理

以下情况必须拒绝输出正式收益，并说明缺少什么、影响什么、如何修复：

- 行动前后范围无法对齐；
- 基线未冻结或数据版本不明；
- 成本、业务量或 SLA 口径不同；
- 执行日期不在基线与观察期之间；
- 行动收益重叠且无法拆分；
- 关键 SLA 数据缺失；
- 承诺采购缺少有效成本或适用期间。

## 11. 测试与验收

必须自动验证：

- 用户数据隔离；
- 合法和非法状态转换；
- 基线不可覆盖；
- 五类行动的验证公式；
- 固定与变动成本拆分；
- 行动前后可比性；
- 重复收益去除；
- SLA 恶化识别；
- 成本规避不进入已实现收益；
- 证据降级与无法验证；
- CSV 导入导出和中文编码；
- Streamlit 页面契约与健康检查。

第一版验收闭环：

```text
标准行动导入
→ 状态推进
→ 上传前后数据
→ 自动选择验证方法
→ 输出可追溯收益或拒绝验证
→ 检查 SLA 副作用
→ 写入 Supabase 收益台账
→ 导出管理层报告
```
